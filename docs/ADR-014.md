# ADR-014: Silver Layer Schema, public.* Retirement, and Transform Design

- **Status:** Accepted
- **Date:** 2026-10-02
- **Deciders:** Data Platform Engineering
- **Phase:** Phase 4A — Silver Layer
- **Supersedes:** ADR-006 (public schema placement), ADR-013 (public.* left unpopulated as candidate Silver contract)

## Context

Phase 4A introduces the Silver layer, which applies type casting, domain constraints, and referential-integrity enforcement to data that was stored verbatim in Bronze. A decision was deferred in ADR-013: whether the `public.*` tables that were created in Phase 1/2B would become the Silver contract or be retired.

After review, the `public.*` tables are structurally identical to the intended Silver schema but reside in the wrong schema and were never populated via the pipeline. Moving them into a dedicated `silver` schema (mirroring the existing `bronze` schema) is cleaner than keeping the medallion layers in mixed schemas.

## Decision

1. **Retire `public.*`:** `sql/init.sql` now executes `DROP SCHEMA IF EXISTS public CASCADE` on a fresh volume. The five relational tables (`facilities`, `customers`, `policies`, `claims`, `payments`) that existed in `public` are no longer created there.

2. **Introduce `silver` schema:** `sql/silver.sql` creates a dedicated `silver` schema with the same five business tables plus `silver.rejected_rows`. All DDL conventions from ADR-003, ADR-009, ADR-010, and ADR-011 are carried forward verbatim:
   - `NUMERIC(12,2)` for money (ADR-003)
   - `ON DELETE RESTRICT` on all foreign keys (ADR-009)
   - Real MOH facility codes as PK/FK for `facilities` and `claims.facility_id` (ADR-010)
   - `facility_category` and `subsector` are `NOT NULL` with no hardcoded `CHECK` constraints (ADR-011)
   - All constraints are named explicitly (`chk_silver_*`, `fk_silver_*`, `idx_silver_*`)

3. **Silver transform (`src/transformation/transform_silver.py`):**
   - Full refresh per run: TRUNCATE all silver tables and `silver.rejected_rows`, then reload inside a single transaction.
   - Reads **only the latest batch** per source table. The latest batch is determined from `bronze.ingestion_log` (most recent `SUCCESS` entry by `finished_at` for the source file). Falls back to latest `_batch_id` in the bronze table if no log entry exists (test convenience).
   - Load order respects referential integrity: facilities and customers first, then policies, then claims, then payments.
   - Type casting: TEXT → DATE, TEXT → NUMERIC (via `Decimal`), TEXT → TIMESTAMPTZ, enums validated against `CHECK` constraint values.
   - Non-crashing error handling: rows that fail to parse or violate referential integrity are written to `silver.rejected_rows` with `source_table`, `source_batch_id`, `source_row_number`, `reject_reason` (human-readable text), and `raw_row` (JSONB). The transform continues; it does not crash on bad rows.
   - Prints a summary table: rows read, rows loaded, rows rejected per table.

4. **`silver.rejected_rows` table:** Purpose-built for row-level rejection tracking. Contains:
   - `source_table TEXT NOT NULL` — which Silver table the row was destined for
   - `source_batch_id UUID` — the bronze batch that produced the row
   - `source_row_number INT` — row position within the bronze batch
   - `reject_reason TEXT NOT NULL` — human-readable rejection cause
   - `raw_row JSONB NOT NULL` — full Bronze row payload for reprocessing
   - `rejected_at TIMESTAMPTZ NOT NULL DEFAULT now()`

5. **`scripts/verify_db_rollback.py`:** Updated to insert into `silver.*` instead of `public.*`. The same constraint rollback verification (all FKs, CHECKs, NOT NULLs) applies to the Silver schema.

## Consequences

- The `public` schema no longer exists in InsureFlow's PostgreSQL database. Any tooling assuming `public.*` tables will need to be updated (none exists in this codebase as of Phase 4A).
- The Silver layer is the first populated, typed layer in the medallion architecture.
- `silver.rejected_rows` provides an audit trail for data quality issues; aggregated DQ reporting and rule enforcement are deferred to Phase 4B.
- Idempotent full-refresh semantics mean re-running `transform_silver.py` after new Bronze ingestion always produces a consistent Silver state.
- No new Python dependencies are introduced; all work uses `psycopg2`, `python-dotenv`, and the standard library.
