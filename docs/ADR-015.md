# ADR-015: Data Quality Rule Framework & Quarantine-Not-Delete Strategy

- **Status:** Accepted
- **Date:** 2026-10-03
- **Deciders:** Data Platform Engineering
- **Phase:** Phase 4B — Data Quality (Defect Injection + DQ Rules)

## Context

In Phase 4A, the Silver transformation layer was implemented with schema-level rejection logging in `silver.rejected_rows`. However, enterprise data engineering requires proactive, testable, and measurable Data Quality (DQ) controls prior to or alongside ingestion.

To ensure data platform reliability, Phase 4B establishes:
1. A composable, multi-dimensional DQ rule framework.
2. Ground-truth evaluation via realistic defect injection and manifest tracking.
3. A strict policy for handling defective records without data loss.

## Decision

1. **Four Core Data Quality Dimensions:**
   All data validation is organized into four foundational dimensions:
   - **Completeness:** Required business fields must not be NULL, empty strings, or placeholder null values.
   - **Uniqueness:** Primary and business keys (e.g. `customer_id`, `policy_id`, `claim_id`, `payment_id`) must remain globally unique within their entity domain.
   - **Validity:** Field values must comply with domain sets (e.g. Malaysian administrative divisions, insurance policy types), calendar date formats (ISO `YYYY-MM-DD`), and numeric boundaries (non-negative currency, valid decimal representation).
   - **Consistency:** Semantic and relational invariants across fields and tables (e.g. `end_date >= start_date`, `approved_amount <= claim_amount`, `claim_date` within policy coverage period, `payment_date >= claim_date`, and dates not in the future relative to the reference date `2026-01-01`).

2. **The "Quarantine-Not-Delete" Principle:**
   - Rows that fail any DQ rule are **never dropped, deleted, or silently overwritten**.
   - Defective records are routed to an isolated quarantine repository (`data/sample/<table>_quarantine.csv` in file-based staging; `silver.rejected_rows` in database ingestion).
   - Each quarantined row preserves the complete original record along with a combined, detailed reason string (`quarantine_reason` / `reason`), identifying every rule that failed.
   - Only records passing 100% of applicable rules proceed to clean consumption datasets (`data/sample/<table>_passed.csv`).

3. **Ground-Truth Validation & Metrics:**
   - `src/quality/inject_defects.py` generates isolated dirty sample datasets (`data/sample/*_dirty.csv`) without altering the clean source files in `data/raw/`.
   - Defects are injected across four distinct categories (`missing_value`, `duplicate_row`, `out_of_range`, `malformed_format`) at controlled rates (~1.5% per category).
   - Every injected modification is recorded in `data/sample/defect_manifest.csv` containing `(file, row_business_key, defect_category, column_affected, original_value, injected_value)`.
   - The DQ runner (`src/quality/run_dq_checks.py`) benchmarks detections against the manifest to compute headline metrics:
     - **Detection Recall:** Percentage of injected defect records successfully quarantined.
     - **False Positives:** Clean records incorrectly quarantined.

4. **Sanity Baseline Constraint:**
   - Running the DQ runner against clean baseline datasets (`data/raw/`) must produce zero or near-zero rule failures and zero quarantined records.

## Consequences

- Full traceability and auditability: every corrupted record is captured with root-cause reasons.
- Zero data loss: upstream systems and data stewards can triage quarantined records directly.
- Standardized rule interface: rules are pure, stateless functions returning structured `RuleFailure` objects, facilitating unit testing and future dbt or Great Expectations adoption.
- No new external runtime dependencies: fully implemented using Python 3.12 standard library and `pandas`.
