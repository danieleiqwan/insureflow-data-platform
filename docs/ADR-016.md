# ADR-016 — Gold Layer: Natural Keys as Dimension Primary Keys

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-03 |
| **Phase** | 5 — Gold Layer |
| **Deciders** | Daniel (project owner) |

## Context

The Gold layer introduces a dimensional (star schema) model in `gold.*`. Every dimension
table needs a primary key. The two standard approaches are:

1. **Natural key** — use the business identifier already present in Silver
   (e.g. `customer_id`, `policy_id`, `facility_id`).
2. **Surrogate key** — generate a new system-assigned integer key (e.g. `SERIAL` /
   `BIGSERIAL`) that is independent of the source value.

## Decision

**Use natural keys** (the same business identifiers from Silver) as the primary keys of
all Gold dimension tables.

`dim_date.date_key` uses the `DATE` type (not `INT YYYYMMDD`) for the same reason:
PostgreSQL and Power BI handle `DATE` natively, avoiding integer arithmetic in BI tools.

## Rationale

| Factor | Natural key | Surrogate key |
|--------|-------------|---------------|
| Simplicity | ✅ No key-mapping layer | ❌ Requires lookup or JOIN to map |
| BI ergonomics | ✅ IDs readable in reports | ❌ Surrogate is opaque to analysts |
| SCD support | ❌ Cannot track history without SCD Type 2 | ✅ Standard SCD2 pattern |
| Portability | ✅ IDs stable across reloads | ❌ Surrogate may change across reloads |
| Scope alignment | ✅ No SCD requirement in Phase 5 | ❌ Over-engineering for current scope |

InsureFlow Phase 5 does **not** require Slowly Changing Dimension (SCD) tracking.
The Silver layer guarantees uniqueness of business keys, so natural keys are safe as PKs.
Full refresh (TRUNCATE + reload) means surrogates would be regenerated each run anyway,
eliminating their main benefit.

## Trade-offs Acknowledged

In a production warehouse, surrogate keys would normally be used to:
- Support SCD Type 2 (tracking historical changes to dimension attributes).
- Decouple Gold from upstream key changes (e.g. if a customer ID format changes).
- Enable standard `IDENTITY`/`SERIAL` patterns for integration with ETL tools.

This project deliberately simplifies: dimensions are **SCD Type 1** (overwrite on reload),
and key format stability is guaranteed by the synthetic data generators.

If SCD support becomes a requirement in a future phase, this ADR should be revisited and
a migration to surrogate keys planned with a dedicated ADR.

## `dim_date.date_key` type choice: `DATE` vs `INT YYYYMMDD`

`DATE` is chosen over `INT YYYYMMDD` because:
- PostgreSQL stores `DATE` in 4 bytes — same as `INT`.
- Power BI (Phase 6) treats `DATE` columns as proper date types without conversion.
- Date arithmetic (e.g. `date_key + INTERVAL '1 day'`) works without casting.
- `INT` keys (e.g. `20250103`) provide no meaningful performance advantage at this scale.

## Consequences

- Gold PK columns mirror Silver PK columns exactly.
- The load script (`load_gold.py`) needs no surrogate-key generation logic.
- A future Phase requiring SCD2 will need an ADR and migration.
